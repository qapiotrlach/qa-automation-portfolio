Java · Cykl wydawniczy

Dlaczego LTS, a nie „najnowsza"

Java wychodzi w nowej wersji głównej co pół roku. Ale tylko część wydań dostaje status LTS (Long-Term Support). Zwykłe wydanie jest wspierane przez jakieś sześć miesięcy — do czasu, aż wyjdzie następne. Potem koniec: żadnych łatek, żadnych poprawek bezpieczeństwa.

LTS-y — 8, 11, 17, 21, 25 — dostają wsparcie przez lata. Dlatego firmy stoją wyłącznie na nich, dlatego ogłoszenia mówią „Java 17" albo „Java 21", i dlatego nikt nigdy nie napisze „szukamy programisty Java 20".

Pułapka licencyjna Oracle

Od Javy 17 Oracle udostępnia swoje JDK na licencji NFTC, która brzmi „za darmo" — ale zawiera zapis: darmowe do roku po ukazaniu się następnego LTS. Ponieważ Java 25 wyszła we wrześniu 2025, aktualizacje Oracle JDK 21 wydane po wrześniu 2026 przechodzą na płatną licencję OTN.

U nas na maszynie

Zastaliśmy Oracle Java 20 — wydanie nie-LTS, bez wsparcia od 2023 roku. Zastąpiliśmy ją Temurin JDK 25 LTS (wsparcie do 2033). Javy 21 świadomie nie wybraliśmy: za dwa miesiące weszlibyśmy prosto w opisaną wyżej ścianę licencyjną.

Pytanie rekrutacyjne

Czym różni się wydanie LTS od zwykłego i dlaczego to ma znaczenie dla projektu?

Zwykłe wydanie jest wspierane ~6 miesięcy, LTS przez lata. Projekt komercyjny żyje dłużej niż pół roku, więc na nie-LTS byłbyś zmuszony do migracji dwa razy w roku albo do stania na wersji bez łatek bezpieczeństwa.

Wartość dodana w odpowiedzi: wspomnieć, że sam status LTS to nie wszystko — liczy się jeszcze licencja konkretnej dystrybucji. Oracle JDK jest darmowy tylko do roku po następnym LTS, więc „LTS" nie znaczy automatycznie „darmowy przez cały okres wsparcia".

Java · Dystrybucje

Java to nie jest jeden produkt

OpenJDK to otwarty kod źródłowy Javy. Nikt nie rozdaje go jako gotowej binarki — firmy biorą ten kod, kompilują i publikują własne dystrybucje: Oracle JDK, Eclipse Temurin, Amazon Corretto, Azul Zulu, Microsoft Build of OpenJDK.

Kod jest praktycznie ten sam. Różnią się licencją, długością wsparcia i tym, kto podpisuje binarkę. To trochę jak dystrybucje Linuksa: jedno jądro, różne opakowanie.

Dlaczego wybraliśmy Temurin

  • Licencja bez haczyków. Fundacja Eclipse, darmowy zawsze i bezwarunkowo. Żadnego liczenia miesięcy.
  • To domyślny wybór w CI. actions/setup-java w GitHub Actions ma Temurina jako standard, podobnie większość obrazów Dockera. Ta sama dystrybucja lokalnie i w pipelinie = mniej „u mnie działa".
  • Certyfikat TCK. Formalnie przeszedł zestaw testów zgodności Oracle. To nie jest podróbka.
Kontekst historyczny

W 2019 Oracle zmienił licencję tak, że komercyjne użycie ich JDK zaczęło wymagać płatnej subskrypcji. Pół branży uciekło wtedy na AdoptOpenJDK (dziś Temurin) i Corretto. Jeśli ktoś na rozmowie pyta „czemu nie Oracle JDK", to jest właśnie ta historia.

Pytanie rekrutacyjne

Jaka jest różnica między OpenJDK a Oracle JDK?

OpenJDK to projekt i kod źródłowy. Oracle JDK to jedna z wielu dystrybucji zbudowanych z tego kodu — obok Temurina, Corretto czy Zulu. Od Javy 11 są funkcjonalnie praktycznie identyczne; realna różnica leży w licencji i wsparciu, nie w kodzie.

System · Zmienne środowiskowe

Dlaczego trzeba otwierać nowy terminal

Zmienne środowiskowe kopiują się z procesu rodzica do dziecka w momencie startu dziecka. Nie istnieje mechanizm „odświeżenia" środowiska w już działającym procesie. Zmiana w rejestrze dotyka tylko procesów uruchomionych po niej.

Dlatego po każdej instalacji trzeba zamknąć terminal i otworzyć nowy. I dlatego usługa Jenkinsa nie widzi zmiennej, którą dodałeś godzinę temu, dopóki jej nie zrestartujesz.

Zaobserwowaliśmy to na żywo

Po instalacji Temurina Twój nowy terminal pokazywał Javę 25, a sesja Claude Code w tym samym czasie uparcie twierdziła, że jest Java 20. Oba wyniki były prawdziwe: proces Claude Code wystartował przed instalacją i ma zamrożoną kopię starego środowiska, którą przekazuje każdemu swojemu dziecku.

Pytanie rekrutacyjne

Ustawiłeś zmienną środowiskową, a aplikacja jej nie widzi. Jak to diagnozujesz?

Najpierw sprawdzam, czy proces został uruchomiony po zmianie — jeśli nie, ma zamrożone stare środowisko i wystarczy restart. Potem sprawdzam zakres: zmienna ustawiona dla użytkownika A nie istnieje dla usługi działającej jako SYSTEM. To najczęstsza przyczyna na serwerach CI.

System · PATH

PATH: kolejność decyduje o wszystkim

PATH to lista katalogów, w których system szuka programu, gdy wpiszesz jego nazwę. Szuka po kolei i bierze pierwszy trafiony. Nie „najnowszy", nie „najlepszy" — pierwszy. Cała reszta jest ignorowana w milczeniu.

Nasz przypadek

Zastaliśmy trzy wpisy Javy naraz. Oracle instaluje własny skrót zwany javapath, który wpycha się na początek listy: 

stan zastany:
1. C:\Program Files\Common Files\Oracle\Java\javapath   ← shim Oracle, wygrywał
2. C:\Program Files\Java\jdk-20\bin

po instalacji Temurina:
1. C:\Program Files\Eclipse Adoptium\jdk-25...\bin      ← Temurin wskoczył przed shim
2. C:\Program Files\Common Files\Oracle\Java\javapath   ← mina
3. C:\Program Files\Java\jdk-20\bin                     ← mina

po sprzątaniu:
1. C:\Program Files\Eclipse Adoptium\jdk-25...\bin      ← jedyna Java

Stan pośredni działał, ale przypadkiem. Wystarczyłby jeden instalator przestawiający kolejność i cicho wróciłbyś na Javę 20.

Martwe wpisy

Deinstalator Oracle usunął katalog jdk-20, ale zostawił po sobie wpis w PATH wskazujący w pustkę. Nie boli, ale każdy martwy wpis to dodatkowy katalog do przeszukania przy każdym uruchomieniu procesu — i szum przy diagnozie.

Pułapka · setx obcina PATH

W internecie krąży rada „użyj setx PATH ...". Nigdy tego nie rób. setx ma twardy limit 1024 znaków i przy dłuższej wartości obcina ją bez ostrzeżenia. Ludzie w ten sposób kasowali sobie C:\Windows\System32 z PATH i orali system.

Poprawna metoda to [Environment]::SetEnvironmentVariable(..., "Machine") — bez limitu, zapis prosto do rejestru. Nasz PATH miał 808 znaków: jedna instalacja od granicy.

Dwie zasady, które warto mieć w odruchu

  • Zawsze backup przed edycją PATH. Jeden plik tekstowy, dwie sekundy roboty.
  • Po edycji sprawdź, czy System32 nadal jest na liście. To ten wpis, którego utrata psuje wszystko.
Pytanie rekrutacyjne

Wpisujesz java -version i dostajesz inną wersję, niż się spodziewasz. Co robisz?

Sprawdzam, który plik wykonywalny się uruchamia — na Windows Get-Command java -All, na Linuksie which -a java. To pokazuje wszystkie trafienia w kolejności PATH. Zwykle winowajcą jest shim albo stary wpis stojący wyżej niż ten właściwy. Osobno sprawdzam JAVA_HOME, bo narzędzia typu Maven kierują się nim, a nie PATH — i te dwie rzeczy potrafią wskazywać co innego.

System · Uprawnienia

UAC: jesteś adminem i jednocześnie nim nie jesteś

Gdy logujesz się na konto z uprawnieniami administratora, Windows wystawia Ci dwa tokeny: pełny administracyjny i przefiltrowany, standardowy. Każdy proces uruchamiany normalnie — Explorer, terminal, IDE — dostaje ten przefiltrowany, z wyciętym członkostwem w grupie Administratorzy.

„Uruchom jako administrator" nie zmienia konta. Wydaje procesowi ten drugi, pełny token. Stąd pozornie sprzeczny wynik, na który trafiliśmy: 

czy proces ma uprawnienia admina?
NIE — token przefiltrowany

czy konto należy do grupy Administratorzy?
LAPTOP-QA\Administrator
LAPTOP-QA\qapio          ← TAK, jesteś tu

Oba zdania prawdziwe naraz. Konto ma uprawnienia; proces ich nie dostał.

Czego nas to nauczyło

Pierwsza próba naszego skryptu zrobiła połowę roboty i nie krzyknęła: backup się zapisał (pulpit nie wymaga uprawnień), a zapis do rejestru poległ po cichu. Dopisaliśmy bezpiecznik sprawdzający uprawnienia na wejściu. Zasada uniwersalna, a w CI krytyczna: fail fast, głośno, zanim cokolwiek zmienisz — nie w połowie i nie po cichu.

Pytanie rekrutacyjne

Skrypt działa, gdy uruchamiasz go ręcznie, ale zawodzi na agencie CI. Od czego zaczynasz?

Od porównania kontekstu wykonania: na jakim koncie działa agent, jakie ma uprawnienia i jakie widzi zmienne środowiskowe. Usługa działająca jako SYSTEM albo dedykowany użytkownik ma inne środowisko i inny token niż Twoja interaktywna sesja. To najczęstsza przyczyna klasy „u mnie działa".

Maven · Konfiguracja

MAVEN_HOME i ostrzeżenie, którego nie wolno zignorować

Zmienne *_HOME wskazują katalog domowy, nie bin

Konwencja jest jednolita dla JAVA_HOME, MAVEN_HOME, ANDROID_HOME: wskazujesz katalog główny, a narzędzia doklejają sobie \bin same. 

stan zastany:
MAVEN_HOME = C:\apache-maven-3.9.1\bin    ← rozwija się do \bin\bin

poprawnie:
MAVEN_HOME = C:\apache-maven-3.9.16       ← katalog domowy

Błąd nie objawiał się, bo sam Maven tej zmiennej nie potrzebuje — znajduje się przez PATH. Ale gdy sięgnie po nią plugin Jenkinsa albo IDE, dostaniesz „nie znaleziono Mavena" i będziesz szukał godzinę.

Ostrzeżenie o jansi — czyli JEP 472

Maven 3.9.1 wiózł ze sobą starą bibliotekę jansi 2.4.0 (koloruje output w konsoli), która ładuje kod natywny przez System::load. Nowsze JDK, w ramach JEP 472, traktują dostęp do kodu natywnego jako operację ograniczoną: 

WARNING: A restricted method in java.lang.System has been called
WARNING: java.lang.System::load has been called by org.fusesource.jansi...
WARNING: Restricted methods will be blocked in a future release

Zwróć uwagę na ostatnią linię: „will be blocked". To nie kosmetyka — to licznik odliczający do wersji JDK, w której build przestanie startować. Aktualizacja Mavena do 3.9.16 wyciszyła ostrzeżenie, bo nowszy Maven wiezie naprawioną jansi.

Pytanie rekrutacyjne

Build wypisuje ostrzeżenia, ale kończy się sukcesem. Zajmujesz się tym?

Tak, i czytam treść zamiast filtrować. Ostrzeżenia z JDK zwykle zapowiadają zmianę, która w kolejnej wersji stanie się twardym błędem — jak JEP 472, gdzie „warning" dziś znaczy „blocked" jutro. Naprawa kosztuje minutę teraz i dzień w środku migracji.

Bezpieczeństwo · Łańcuch dostaw

Suma kontrolna z innego serwera niż plik

Przy pobieraniu Mavena użyliśmy dwóch różnych hostów i to jest sedno, a nie szczegół: 

plik ZIP    → https://dlcdn.apache.org/...       CDN / lustro
suma SHA512 → https://downloads.apache.org/...  główny serwer Apache

Apache rozdaje binarki przez sieć luster, bo są duże i ruch jest spory. Lustro to cudza infrastruktura — Apache jej nie kontroluje. Gdyby ktoś podmienił ZIP na lustrze, dostałbyś zatrutego Mavena, który wygląda normalnie i buduje Twój projekt.

Dlatego sumę kontrolną pobiera się z serwera głównego, nigdy z tego samego miejsca co plik. Atakujący musiałby złamać oba naraz.

Kolejność ma znaczenie

Weryfikuj przed rozpakowaniem, nie po instalacji. Sprawdzanie sumy po zainstalowaniu pliku jest teatrem — kod już jest na dysku.

Pytanie rekrutacyjne

Co to jest atak na łańcuch dostaw i jak się przed nim bronić?

To atak nie na Twój kod, tylko na coś, czemu Twój kod ufa: zależność, narzędzie budujące, obraz bazowy, plugin CI. Obrona to weryfikacja sum kontrolnych i podpisów z niezależnego źródła, pinowanie wersji zamiast zakresów, lockfile w repozytorium i automatyczne skanowanie zależności.

Kontekst dla QA: testy uruchamiane w CI mają zwykle dostęp do sekretów i środowisk. Zatruta zależność w projekcie testowym bywa łatwiejszym celem niż produkcja.

PowerShell · ExecutionPolicy

ExecutionPolicy nie jest zabezpieczeniem

Domyślnie Windows kliencki ma politykę Restricted — żaden skrypt .ps1 nie może się uruchomić. Node instaluje dwa opakowania na npm: npm.cmd i npm.ps1. W PowerShellu wygrywa wersja .ps1 i odbija się od polityki — stąd nasz błąd, mimo że npm był w pełni sprawny. 

        Scope ExecutionPolicy
      Process          Bypass      ← sesja Claude Code
  CurrentUser       Undefined     ← Twoja → efektywnie Restricted
 LocalMachine       Undefined

Precedencja idzie z góry na dół. Dlatego moje skrypty chodziły, a Twoje nie — ta sama mechanika, o którą rozbijają się ludzie na Jenkinsie, gdzie agent ma inną politykę niż terminal.

Częste nieporozumienie

To nie jest mechanizm bezpieczeństwa i Microsoft mówi to wprost. Omija się go trywialnie: powershell -ExecutionPolicy Bypass -File zly.ps1 albo przepuszczeniem treści przez potok. To bariera przed przypadkowym uruchomieniem skryptu, np. dwuklikiem w załącznik z maila. Nie licz na nią jako na ochronę.

Wartości, które warto znać

WartośćZnaczenie
Restrictedżadnych skryptów · domyślne na Windows klienckim
RemoteSignedlokalne działają, pobrane wymagają podpisu · nasz wybór
AllSignedkażdy skrypt musi być podpisany, również Twój własny
Bypassbez ograniczeń · typowe dla agentów CI

Windows rozpoznaje pobrane pliki po znaczniku Mark of the Web, który przeglądarka dokleja do pliku. Wybraliśmy RemoteSigned w zakresie CurrentUser — zasada najmniejszych uprawnień: nie ruszaj całej maszyny, gdy wystarczy ruszyć siebie.

Node.js · Cykl wydawniczy

Ta sama logika, co przy Javie: do projektu, który ma stać latami, bierzesz linię z długim wsparciem, a nie najświeższą. Node 26 jest „Current", czyli linią rozwojową — LTS-em stanie się dopiero jesienią.

Wiedza, która się właśnie dezaktualizuje

Klasyczna zasada brzmi „parzyste wersje Node to LTS, nieparzyste nie". Od wersji 27 (październik 2026) Node przechodzi na jedno wydanie główne rocznie i każde będzie LTS-em — podział znika. Jeśli ktoś przytoczy tę regułę na rozmowie, od jesieni będzie już nieaktualna. Dobre miejsce, żeby pokazać, że śledzisz temat.

Linux · WSL

WSL: Linux w środku Windowsa

WSL (Windows Subsystem for Linux) pozwala uruchomić pełne Ubuntu wewnątrz Windowsa — bez dual boota, bez VirtualBoxa, bez osobnego okna maszyny wirtualnej. Otwierasz terminal i jesteś w Linuksie, mając jednocześnie dostęp do plików Windowsa.

WSL1 kontra WSL2 — to dwie zupełnie różne rzeczy

Nazwa sugeruje wersję tego samego, ale to fundamentalnie inna architektura. To jedno z tych rozróżnień, które bardzo dobrze wypada na rozmowie.

WSL1WSL2
Jak działa warstwa tłumacząca wywołania systemowe Linuksa na wywołania Windowsa prawdziwe jądro Linuksa w lekkiej maszynie wirtualnej
Jądro Linuksa brak — jest emulowane jest, dostarczane i aktualizowane przez Microsoft
Zgodność częściowa — część wywołań nie istnieje pełna
Docker nie działa działa
Szybsze przy plikach na dyskach Windows (/mnt/c) plikach we własnym systemie ext4

Dlaczego Docker wymaga akurat WSL2

Kontenery to nie maszyny wirtualne. Kontener to proces Linuksa odizolowany mechanizmami samego jądra — namespaces (izolacja: własne PID-y, sieć, punkty montowania) i cgroups (limity: ile CPU, ile pamięci).

To są funkcje jądra Linuksa. WSL1 jądra nie ma, tylko tłumacza wywołań — więc nie ma czego użyć. WSL2 ma prawdziwe jądro, więc kontenery działają natywnie. To cała odpowiedź na pytanie „czemu Docker potrzebuje WSL2".

Konsekwencja przy pracy z plikami

Skoro WSL2 to osobna maszyna wirtualna z własnym dyskiem, to dostęp do plików Windowsa (/mnt/c/...) idzie przez sieć i jest wolny. Projekt trzymany w /mnt/c i budowany z WSL2 potrafi być kilkukrotnie wolniejszy niż ten sam projekt w natywnym systemie plików WSL-a. Klasyczne źródło „czemu to tak muli".

Dlaczego to działa na Windows 10 Home

Pełny Hyper-V rzeczywiście jest tylko w edycjach Pro i Enterprise. Ale WSL2 nie używa pełnego Hyper-V — korzysta z funkcji Virtual Machine Platform, czyli okrojonego hipernadzorcy dostępnego również w Home. Właśnie po to Microsoft ją wydzielił.

To też wyjaśnia, dlaczego Docker Desktop z backendem WSL2 działa na Home, mimo że stary backend oparty na Hyper-V nigdy nie działał.

U nas

WSL-a nie było w ogóle — wsl --list zwracał samą pomoc, czyli zero dystrybucji. Wirtualizacja w BIOS-ie jest już włączona (HypervisorPresent: True), więc odpadła najgorsza część: grzebanie w BIOS-ie. Komenda wsl --install robi cztery rzeczy naraz: włącza funkcję Subsystem for Linux, włącza Virtual Machine Platform, pobiera jądro Linuksa i instaluje Ubuntu. Wynik końcowy: 

Ubuntu 26.04 LTS
6.18.33.2-microsoft-standard-WSL2   ← dowód: prawdziwe jądro Linuksa
uid=1000(qapiolac) ... 27(sudo) ...  ← użytkownik w grupie sudo
Dwie pułapki, na które trafiliśmy

Restart musi być restartem. Windows 10 ma domyślnie włączone szybkie uruchamianie — „Zamknij system" nie robi pełnego wyłączenia, tylko hibernuje jądro. Składniki systemu nie inicjalizują się od nowa i wracasz do tego samego stanu. Tylko „Uruchom ponownie" wymusza pełny cykl. Stąd klasyczne „przecież wyłączałem komputer, a dalej nie działa".

„Oczekiwanie na ukończenie OOBE" to nie zawieszenie. OOBE (Out Of Box Experience) to pierwsza konfiguracja Ubuntu. Komunikat znaczy dosłownie to, co pisze: WSL czeka, aż skończysz w osobnym oknie. Diagnoza: proces zużył 0,1 s CPU przez 34 minuty — zawieszony proces zwykle miele procesor albo puchnie, a ten po prostu czekał na klawiaturę.

Pytanie rekrutacyjne

Czym różni się kontener od maszyny wirtualnej?

Maszyna wirtualna emuluje cały sprzęt i uruchamia własne, pełne jądro systemu — stąd waga liczona w gigabajtach i start w minutach. Kontener to zwykły proces na współdzielonym jądrze hosta, odizolowany przez namespaces i ograniczony przez cgroups — stąd megabajty i start w sekundach.

Konsekwencja: kontener nie niesie własnego jądra, więc kontenery Linuksa potrzebują jądra Linuksa. Na Windowsie dostarcza je właśnie WSL2 — i dlatego Docker Desktop go wymaga.

Docker · Konteneryzacja

Docker — i dlaczego to narzędzie testera, nie tylko dewelopera

Problem, który rozwiązuje

Projekt potrzebuje bazy PostgreSQL, backendu Javy, frontendu Node, serwera pocztowego i trzech przeglądarek do Grida. Bez Dockera instalujesz każdą z tych rzeczy ręcznie na swoim laptopie — porty, użytkownicy bazy, zmienne. Potem okazuje się, że na Jenkinsie stoi inna wersja PostgreSQL i testy padają. Klasyczne „u mnie działa".

Docker zamyka każdy element w kontenerze — samowystarczalnej paczce z aplikacją i jej zależnościami. Jedna komenda podnosi, jedna kasuje, na laptopie nie zostaje ślad.

Analogia OOP klasa obiekt

Dlaczego kontener jest lekki

Kontener to proces Linuksa odizolowany przez namespaces (własne PID-y, sieć, system plików) i ograniczony przez cgroups (limity CPU i pamięci) — mechanizmy jądra hosta. Nie niesie własnego jądra ani systemu, więc waży megabajty i wstaje w sekundę. Maszyna wirtualna niesie jedno i drugie, więc waży gigabajty i wstaje w minutę. Szczegóły w sekcji WSL i WSL2.

Po co to testerowi — konkretnie

  • Selenium Grid bez instalowania przeglądarek. Chrome, Firefox i Edge w kontenerach, każdy z przypiętą wersją — koniec z automatycznymi aktualizacjami przeglądarki psującymi testy w nocy.
  • Czysta baza na każdy przebieg. Największa zmora testów E2E to dane po poprzednim uruchomieniu. Kontener podnosisz przed, kasujesz po. Stan zerowy, zawsze.
  • Testcontainers. Biblioteka, w której kod testu sam podnosi kontener z bazą, dostaje losowy port, a po teście kontener znika. Bez Dockera nie istnieje, a jest dziś standardem testów integracyjnych w Javie.
  • Ten sam obraz lokalnie i w CI. Jenkins uruchamia dokładnie ten obraz, który testujesz u siebie. Nie ma dwóch środowisk, więc nie ma się czemu rozjechać.
  • Całe portfolio jedną komendą. docker compose up podnosi backend, frontend, bazę i pocztę naraz. To ta komenda, którą wpisze rekruter — albo mu zadziała w minutę, albo zamknie kartę.
Uczciwie: czy da się bez tego

Da się — zainstalowane lokalnie wszystko będzie działać. Na Twoim laptopie. Ale Docker jest w ogłoszeniach na Senior QA praktycznie zawsze, a cały nowoczesny CI stoi na kontenerach. Pomijając go, wycinasz połowę wartości projektu z portfolio.

U nas · pamięć

WSL2 domyślnie rezerwuje połowę RAM-u — na naszych 11 GB zabrał 5,3 GB, dokładnie zgodnie z przewidywaniem. Z IntelliJ i przeglądarkami zrobi się ciasno, więc limity przez plik .wslconfig będą potrzebne.

Pytanie rekrutacyjne

Jaka jest różnica między obrazem a kontenerem?

Obraz to niezmienny szablon leżący na dysku. Kontener to jego działająca instancja — z jednego obrazu można uruchomić wiele niezależnych kontenerów. Jak klasa i obiekt.

Pytanie rekrutacyjne

Do czego wykorzystujesz Dockera w automatyzacji testów?

Do trzech rzeczy przede wszystkim: izolacji danych testowych (czysta baza na każdy przebieg zamiast sprzątania po poprzednim), uruchamiania Selenium Grida z przypiętymi wersjami przeglądarek, oraz zapewnienia, że lokalnie i w CI działa dokładnie to samo środowisko.

Wartość dodana: wspomnieć Testcontainers — że zależności podnosi sam test, a nie ręcznie przygotowane środowisko. To pokazuje, że myślisz o powtarzalności, a nie tylko o „odpaleniu testów".

Git · Konfiguracja

Ustawienia, które ratują przed konkretnymi błędami

Końce linii — mina, która wybucha w Dockerze

Windows kończy linie znakami CRLF, Linux i macOS samym LF. Git potrafi konwertować to automatycznie i domyślne ustawienie na Windowsie (core.autocrlf=true) robi to za Twoimi plecami.

Problem ujawnia się dopiero w kontenerze:

/bin/bash^M: bad interpreter: No such file or directory

Ten ^M to niewidzialny znak CR. Plik wygląda w edytorze absolutnie normalnie — stąd godziny straconego czasu.

Rozwiązanie: core.autocrlf=false (Git niczego nie tłumaczy) plus plik .gitattributes w repozytorium, który dekretuje końce linii per typ pliku. Konfiguracja w repo bije konfigurację na maszynie — działa jednakowo u Ciebie, na Jenkinsie i u każdego, kto sklonuje projekt.

core.longpathstrue„Filename too long" przy node_modules (limit 260 znaków w Windows)
pull.rebasetrueśmieciowe commity „Merge branch 'main' of…"

Adres e-mail w commitach

Każdy commit zawiera adres e-mail autora, a historia Git jest publiczna — wystarczy git log, żeby wyciągnąć wszystkie adresy z repozytorium. Spamerzy scrapują GitHuba właśnie po to.

Dlatego używamy adresu zastępczego ID+nazwa@users.noreply.github.com. GitHub normalnie przypisze commity do konta i zaliczy je do wykresu aktywności, ale prawdziwy adres pozostaje ukryty. W ustawieniach konta warto włączyć też Block command line pushes that expose my email — bezpiecznik na wypadek pracy z innej maszyny.

Pułapka · tylda i powłoki

~/.ssh/id_ed25519.pub zadziała w bashu, ale nie w PowerShellu. Tylda to funkcja powłoki: bash rozwija ją do katalogu domowego zanim przekaże argument programowi, PowerShell przekazuje programom zewnętrznym dosłowny tekst ~/.... Efekt: „System nie może odnaleźć określonej ścieżki". W PowerShellu używaj $env:USERPROFILE lub pełnych ścieżek.

Conventional Commits

Format typ: opis ze stałym zestawem typów: feat, fix, test, refactor, docs, chore, ci. Pierwsza linia w trybie rozkazującym, do 72 znaków, bez kropki; szczegóły po pustej linii.

To nie ozdobnik — na tej konwencji stoi automatyczne generowanie changelogów i wersjonowanie semantyczne: narzędzia czytają typy commitów i same decydują o podbiciu wersji. Rekruter przeglądający historię widzi od razu, czy pracujesz jak w projekcie komercyjnym, czy piszesz „poprawki", „zmiany", „update2".

Git · Podpisy kryptograficzne

Dlaczego commity trzeba podpisywać

Pola author i committer w Gicie to zwykły tekst, którego nikt nie weryfikuje. Każdy może ustawić sobie Twoje imię i adres, zrobić commit i wypchnąć go do repozytorium, do którego ma dostęp. W historii będzie wyglądał jak Twój. 

git config user.name "Linus Torvalds"
git config user.email "torvalds@linux-foundation.org"
git commit -m "cokolwiek"   ← i historia mówi, że to on

Podpis kryptograficzny to rozwiązuje: commit zostaje podpisany kluczem prywatnym, a GitHub weryfikuje go kluczem publicznym i oznacza plakietką Verified.

Wybraliśmy SSH: jeden klucz ed25519 obsługuje logowanie i podpisywanie. GPG wciąż spotyka się w firmach, więc warto wiedzieć, że istnieje.

Klucz uwierzytelniający ≠ klucz podpisujący

Choć u nas to fizycznie ten sam plik, GitHub traktuje te role jako dwa osobne wpisy. Klucz dodany tylko jako Authentication key pozwoli robić push, ale commity będą oznaczone Unverified — GitHub nie wie, że wolno mu tym kluczem weryfikować podpisy. Trzeba dodać go drugi raz jako Signing key.

ssh-agent — bez niego passphrase przy każdej operacji

Klucz chroniony hasłem jest bezpieczny, ale bez agenta Windows pyta o nie przy każdym pushu i każdym commicie. Usługa ssh-agent jest domyślnie wyłączona — trzeba ją włączyć i ustawić na Automatic.

Subtelniejsza pułapka: na Windowsie są dwa różne ssh.exe — systemowy OpenSSH i ten dołączony do Git for Windows. Git domyślnie używa swojego, który nie rozmawia z windowsową usługą. Włączasz agenta, wczytujesz klucz, a Git dalej pyta o hasło. Lekarstwo: 

git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"
Pytanie rekrutacyjne

Po co podpisywać commity, skoro Git i tak zapisuje autora?

Bo pole autora to niezweryfikowany tekst — każdy może się pod kogoś podszyć. Podpis kryptograficzny dowodzi, że commit pochodzi od posiadacza klucza prywatnego. Ma to znaczenie przy audycie i przy atakach na łańcuch dostaw: w repozytorium z wymuszonymi podpisami podrzucony commit zostanie odrzucony.

Bezpieczeństwo · Repozytorium

Sekret w repozytorium zostaje tam na zawsze

Zdarzyło się u nas

Przy pierwszym git add -A do commita podczepił się plik github-recovery-codes.txt — kody zapasowe 2FA, zapisane wcześniej na pulpicie. Kto ma te kody, omija dwuskładnikowe uwierzytelnianie i przejmuje konto. Plik został wyjęty przed commitem i dopisany do .gitignore.

Dlaczego usunięcie pliku nie wystarcza

Git przechowuje całą historię. Skasowanie pliku kolejnym commitem usuwa go z bieżącego stanu, ale zawartość zostaje w historii i da się ją odczytać jedną komendą. Jeśli sekret trafił na publiczne repozytorium, należy przyjąć, że wyciekł: boty skanują nowe commity na GitHubie w czasie liczonym w sekundach.

Właściwa reakcja to unieważnienie sekretu — zmiana hasła, rotacja tokenu, wygenerowanie nowych kodów — a dopiero potem czyszczenie historii (git filter-repo). Kolejność ma znaczenie: czyszczenie historii bez rotacji to iluzja bezpieczeństwa.

  • .gitignore piszesz przed pierwszym commitem, nie po.
  • Sekrety nie mieszkają w katalogu projektu — wszystko w nim trafia pod kontrolę Gita.
  • git status przed commit — przejrzyj listę, nie ufaj add -A w ciemno.
  • W CI sekrety idą przez mechanizm sekretów (GitHub Secrets, Jenkins Credentials), nigdy do repo.
Pytanie rekrutacyjne

Hasło do bazy trafiło do publicznego repozytorium. Co robisz?

Najpierw zmieniam hasło — od momentu publikacji trzeba je uznać za skompromitowane, bo boty skanują nowe commity w kilka sekund. Dopiero potem czyszczę historię i dodaję plik do .gitignore. Na koniec sprawdzam logi dostępu pod kątem nieautoryzowanego użycia i wprowadzam skanowanie sekretów w pipeline, żeby wychwycić kolejny taki przypadek automatycznie.

Git · Strategie pracy z gałęziami

GitFlow a trunk-based development

Pytanie „jaką strategię branchowania stosowaliście i dlaczego” pada na rozmowach bardzo często. Odpowiedź „znam obie i w tym projekcie wybrałem tę, bo…” brzmi zupełnie inaczej niż „robiliśmy tak, jak było”.

GitFlow

main        produkcja; każdy commit = wydana wersja
develop     integracja; tu spływa wszystko do następnego wydania
feature/*   od develop  → do develop
release/*   od develop  → do main ORAZ z powrotem do develop
hotfix/*    od main     → do main ORAZ z powrotem do develop

Powstał w 2010 roku dla oprogramowania wydawanego w wersjach, gdzie równolegle utrzymuje się wersję 2.x i szykuje 3.0. Autor, Vincent Driessen, dopisał w 2020 roku do swojego artykułu, że przy dostarczaniu ciągłym (continuous delivery) poleca prostszy przepływ.

Trunk-based development

Jedna główna gałąź, krótko żyjące gałęzie zadaniowe, szybkie scalanie. Jakości pilnuje pipeline, nie dodatkowa gałąź: PR nie da się scalić, dopóki testy nie przejdą. Rolę bufora, którą w GitFlow pełni develop, przejmują testy automatyczne.

Gałąź w GitFlowŚrodowiskoCo testuje QA
feature/*lokalnie / środowisko PRnową funkcję w izolacji
developtest / devintegrację: czy funkcje działają razem
release/*staging / UATregresję przed wydaniem, „zamrożenie”
mainprodukcjasmoke testy po wdrożeniu
hotfix/*stagingpoprawkę i regresję wokół niej
Dwa klasyczne błędy w GitFlow

PR do złej gałęzi. gh pr create domyślnie celuje w main, a w GitFlow zadanie idzie do develop. Trzeba podać --base develop.

Zapomniany powrót hotfixa do develop. Poprawka trafia na produkcję, ale nie wraca do gałęzi rozwojowej — i przy następnym wydaniu naprawiony błąd wraca na produkcję.

Nasz wybór

Trunk-based, bo projekt jest rozwijany w sposób ciągły, a nie wydawany w wersjach. Doszła też przyczyna techniczna: mamy wymuszoną liniową historię i scalanie wyłącznie przez squash. Squash z develop do main tworzy commit, którego develop nie zna, więc gałęzie rozjeżdżają się po pierwszym wydaniu. GitFlow zakłada zwykłe merge commity — czyli dokładnie to, co wyłączyliśmy.

Wydania pokazujemy tagami i GitHub Releases (v0.1.0, v0.2.0…), co daje efekt „wydaję wersję” bez dodatkowej gałęzi.

Pytanie rekrutacyjne

Jaką strategię pracy z gałęziami stosowaliście?

Warto opisać przepływ i powiązać go z testowaniem: która gałąź trafiała na które środowisko i jakie testy tam działały. Np. „na develop szła nocna regresja, na release testy akceptacyjne, po wdrożeniu na main smoke”. To pokazuje, że rozumiesz proces, a nie tylko komendy.

CI · Pułapki środowiskowe

Drobiazgi, które wywracają build na agencie

Bit wykonywalności pliku

Windows nie ma uniksowego bitu wykonywalności, ale Git go przechowuje i przenosi na inne systemy. Plik utworzony na Windowsie trafia do repozytorium jako 100644, czyli zwykły. Na agencie z Linuksem: 

$ ./mvnw test
./mvnw: Permission denied

Naprawa nie zmienia treści pliku, tylko jego tryb:

git update-index --chmod=+x app/backend/mvnw

przed: 100644 bd8896b… mvnw
po:    100755 bd8896b… mvnw   ← ten sam skrót treści

Kontener, który padł, jest niewidoczny

docker compose ps pokazuje tylko działające kontenery. Gdy kontener wystartował i natychmiast się wywrócił, zobaczysz pustą listę i pomyślisz, że nic się nie uruchomiło. Diagnoza zawsze wygląda tak samo: 

docker ps -a          ← STATUS pokaże "Exited (1)"
docker logs nazwa     ← przyczyna prawie zawsze jest w logach
U nas · PostgreSQL 18 zmienił ścieżkę danych

Do wersji 17 wolumen montowało się pod /var/lib/postgresql/data i tak podaje każdy tutorial. Od 18 obraz trzyma dane w podkatalogu z numerem wersji, żeby umożliwić pg_upgrade, i oczekuje montowania o poziom wyżej: /var/lib/postgresql. Stara ścieżka powoduje wyjście z kodem 1 tuż po starcie.

To argument za przypinaniem wersji obrazów. Przy postgres:latest ta awaria przyszłaby sama, w losowym momencie, bez żadnej zmiany z Twojej strony.

Cudzysłowy w PowerShellu przy curl

JSON przekazany do curl.exe -d wprost w PowerShellu rozpada się, zanim dotrze do narzędzia — serwer odpowiada 400 Bad Request i szuka się błędu po stronie API, którego tam nie ma. Rozwiązanie: zapisz treść do pliku i użyj -d "@plik.json". Uwaga też na samo curl — w PowerShellu to alias na Invoke-WebRequest, inne narzędzie o tej samej nazwie.

Baza danych · Migracje

Schemat bazy jako kod

Flyway wykonuje ponumerowane pliki SQL i zapisuje w tabeli flyway_schema_history, co już zostało wykonane. Schemat każdego środowiska jest dzięki temu odtwarzalny i wiadomo, w jakiej jest wersji. 

V1__init.sql            tabela products
V2__seed_products.sql   dane startowe
format: V<numer>__<opis>.sql — dwa podkreślenia
Migracji nie edytuje się po wypchnięciu

Flyway trzyma sumę kontrolną każdego pliku. Zmiana treści migracji, która gdzieś już się wykonała, kończy się odmową startu aplikacji. Poprawki robi się nową migracją. To celowe: inaczej historia schematu przestałaby być wiarygodna.

Pytanie rekrutacyjne

Jak zapewniasz, że baza na środowisku testowym odpowiada produkcji?

Schemat jest wersjonowany migracjami w repozytorium i wykonywany tak samo na każdym środowisku, a aplikacja startuje z ddl-auto=validate, więc niezgodność encji ze schematem zatrzymuje start zamiast ujawnić się w trakcie testów. Różnicą między środowiskami pozostają wtedy tylko dane, nie struktura.

API · Model danych

Encja, DTO i dlaczego pieniądze to nie double

Encja musi być klasą, rekord nie wystarczy

Rekordy zastępują Lomboka, ale nie nadają się na encje JPA: rekord jest niemutowalny i nie ma konstruktora bezargumentowego, a JPA tworzy obiekt pusty i dopiero wypełnia go danymi z bazy. Rekordy zostają tam, gdzie pasują — w DTO.

Po co osobne DTO

  • Encja opisuje bazę, DTO opisuje kontrakt API. To dwie różne rzeczy, które zmieniają się z różnych powodów.
  • Zwracanie encji wprost sprawia, że każda zmiana kolumny natychmiast zmienia API — i psuje testy oraz klientów.
  • Pola wrażliwe (hasło, token) wyciekłyby do odpowiedzi automatycznie.
  • DTO wejściowe ma własną walidację, niezależną od ograniczeń bazy.
Pieniądze: BigDecimal, nigdy double

Liczby zmiennoprzecinkowe nie potrafią dokładnie zapisać ułamków dziesiętnych — 0.1 + 0.2 daje 0.30000000000000004. Przy koszyku i fakturach kończy się to groszowymi rozjazdami, których nikt nie umie wyjaśnić. W bazie NUMERIC(10,2), w Javie BigDecimal.

API · Kontrakt błędów

Jeden kształt błędu w całym API (RFC 9457)

Domyślnie Spring zwraca ubogą odpowiedź, z której nie wynika, co jest nie tak: 

{"timestamp":"...","status":400,"error":"Bad Request","path":"/api/products"}

Standard RFC 9457 (Problem Details) definiuje wspólny kształt błędu, zwracany z typem application/problem+json: 

{
  "type":   "https://qa-playground/errors/validation",
  "title":  "Blad walidacji",
  "status": 400,
  "detail": "Zadanie zawiera nieprawidlowe dane",
  "instance": "/api/products",
  "violations": [
    { "field": "name",  "message": "Nazwa jest wymagana" },
    { "field": "price", "message": "Cena nie moze byc ujemna" }
  ]
}

W Springu realizuje to @RestControllerAdvice z klasą ProblemDetail: jedno miejsce zamienia wyjątki na odpowiedzi, zamiast obsługi błędów rozsianej po kontrolerach.

Dlaczego to ważne dla testera

Skoro każdy błąd ma ten sam kształt, w testach piszesz jedną metodę sprawdzającą błędy zamiast dopasowywać się do innego formatu przy każdym endpoencie. Pole type jest stabilnym identyfikatorem rodzaju błędu — asercja na nim nie pęknie, gdy ktoś poprawi literówkę w komunikacie dla użytkownika.

Pytanie rekrutacyjne

Na co zwracasz uwagę, testując obsługę błędów w API?

Czy kod odpowiedzi jest właściwy (400 przy błędnych danych, 404 przy braku zasobu, 409 przy konflikcie), czy kształt błędu jest spójny w całym API, czy komunikat nie ujawnia szczegółów implementacji, np. zapytań SQL i stack trace, oraz czy odpowiedź zawiera informację wystarczającą do naprawy — na przykład które pole jest nieprawidłowe.
